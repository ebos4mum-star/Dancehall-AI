Project: `vvwjhbsyxetnktimgaxg` (development, us-east-2). Four migrations remain: **household, wellness, household_join_limit, celebrations** (`habits` is already applied; do not apply it again).

## Why this procedure exists

The migration tool in the assistant's session asks the Supabase server for a confirmation before running some migrations. The prompt is shown to the person at the session, and the session has no way to wait for it: the call is cut off after 60 seconds, twice, with nothing applied. The connector itself is healthy (installed, connected, `habits` applied through it). Only the two migrations that contain `DELETE FROM` inside function bodies (household, household_join_limit) fit the pattern of a destructive-statement confirmation; the others probably would not prompt, but order matters, so all four are provided here. The assistant has not worked around the prompt with another tool.

**Faster alternative:** if you can be at the claude.ai session and approve the prompt within the 60 seconds, ask the assistant to retry `household` with the official tool and skip this procedure.

## What you will run

Each `NN_name.sql` is one transaction: identity, order and re-run guards, then the **exact repository migration text**, then its history row (apply-time version, name, text), then commit. If anything fails nothing is applied and nothing is recorded. The scripts are generated by `scripts/make-owner-apply.mjs` and checked by CI.

## Order and steps (do not skip ahead)

Before step 1: open the project **`vvwjhbsyxetnktimgaxg`** in the Supabase Dashboard (check the project ID in the URL or Project Settings), then Database, Migrations. You should see 9 migrations ending with `habits`. If not, stop.

For each step N = 1, 2, 3, 4, in order:

1. Open SQL Editor, new query, paste the whole of `NN_name.sql`, and Run. The Dashboard may show a confirmation about destructive statements because the file contains `DELETE FROM` inside functions; that confirmation is yours to give. Expected result: success, no rows. An error mentioning "Wrong project", "already recorded" or "Out of order" means nothing was changed; stop and tell the assistant.
2. In a new query paste the whole of `verify_NN_name.sql` and Run **immediately**. Every row must show `ok = true`, and the last row must be `ALL OK` with `ok = true`. Run `verify_01` right after step 1 only (step 3 replaces `household_join`, so verify_01 correctly turns false afterwards).
3. Reply "step N done" and paste the verify output (it holds no secrets) before starting step N+1. If any row is false, stop.

After step 4 run `verify_05_final.sql` (the whole public schema compared with a clean build of all 13 migrations, plus 13 history rows) and send the result.

## Migration history

Each script inserts its own row into `supabase_migrations.schema_migrations` with the same shape the tool writes (apply-time version, name, statements). After all four the history is the existing 9 rows plus `household`, `wellness`, `household_join_limit`, `celebrations`. Do not use `supabase migration repair --status reverted` or `db push`; the existing rows are real history.

## Rollback limits

- Before commit (a failed or interrupted script) everything rolls back automatically.
- After a successful run there is no automatic undo. The new tables hold no user data yet, so dropping them would currently lose nothing, but it is irreversible once people use the app, and the history row would also have to be removed. Do not roll back without telling the assistant; the safe fix for a wrong migration is a new corrective migration.
- Step 3 replaces `household_join` in place; the previous body is the one in `20261208000100_household.sql`.
