## 5. Exact build and upload steps (none have been run)

### 5a. One-time preparation

1. Do 4b (Apple) and 4c (GitHub environments, secrets, variables).
2. Resolve the two workflow prerequisites in section 0 (workflows on `main`; the `check:workspace` rule).
3. Decide the build number. First build: `1`. Every later build for version `0.1.0` needs a higher whole number (App Store Connect rejects a repeat).

### 5b. Build the signed IPA (stops there; approval = approving the `testflight-build` environment)

```bash
gh workflow run ios-testflight-build.yml --ref main \
  -f release_sha=<the full 40-character commit SHA on claude/ecstatic-meitner-8you9v> \
  -f release_branch=claude/ecstatic-meitner-8you9v \
  -f build_number=1 \
  -f confirm=BUILD-SIGNED-IPA
```

(or Actions, "iOS TestFlight build (signed IPA, no upload)", Run workflow). The run: validates the inputs and that the commit is on the branch; runs the release validation (checks, format, lint, types, tests); waits for the environment approval; checks the environment (staging only); generates the project; sets the build number; verifies version, HealthKit entitlement and privacy manifest; installs pods; checks the certificate and profile belong together (Apple Distribution, your team, App Store profile for the bundle id, HealthKit, not expired, lists that certificate); signs the app target manually; archives and exports; inspects the IPA; **encrypts** it (AES-256, passphrase from the secret) and keeps it for 7 days; always removes the keychain and signing files. The summary shows the IPA's sha256 and the run id. **Nothing is sent to Apple.**

### 5c. Upload (separate workflow, separate approval; validate first)

```bash
# 1. Validate only (default): decrypts, re-checks, and asks App Store Connect to validate. Uploads nothing.
gh workflow run ios-testflight-upload.yml --ref main \
  -f build_run_id=<run id from the build summary> -f release_sha=<same SHA> -f build_number=1 \
  -f ipa_sha256=<sha256 from the build summary> -f dry_run=true -f confirm=UPLOAD-TO-TESTFLIGHT

# 2. Only after you approve the upload: the same command with dry_run=false.
gh workflow run ios-testflight-upload.yml --ref main \
  -f build_run_id=<run id> -f release_sha=<same SHA> -f build_number=1 \
  -f ipa_sha256=<sha256> -f dry_run=false -f confirm=UPLOAD-TO-TESTFLIGHT
```

Each run needs its own approval of the `testflight-upload` environment. The workflow refuses an IPA whose hash differs from the build run's. After a real upload, App Store Connect processes the build (minutes), then add it to the internal group (TestFlight tab). **Unverified:** `xcrun altool --upload-app` with an API key is what the workflow uses; if Xcode 26.6 rejects it, the replacement is Apple's Transporter (`xcrun iTMSTransporter`) with the same key, a one-step change in that workflow.
