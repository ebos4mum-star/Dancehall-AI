### 2c. Is the current EAS profile suitable for TestFlight? **No.**

`staging-preview` is `distribution: internal`, which EAS signs with an **ad hoc** provisioning profile for registered devices. Apple does not accept ad hoc archives into TestFlight (App Store Connect rejects them at upload). It also cannot be assumed to be installable by a tester who is not a registered device.
**Added, without triggering a build: profile `staging-testflight`** in `apps/mobile/eas.json`:

```json
"staging-testflight": {
  "distribution": "store",
  "environment": "staging",
  "autoIncrement": true,
  "env": { "EXPO_PUBLIC_APP_ENV": "preview", "EXPO_PUBLIC_AUTH_MODE": "supabase", "EXPO_PUBLIC_CLOUD_ACCOUNTS": "1",
           "EXPO_PUBLIC_SOCIAL": "1", "EXPO_PUBLIC_COMMUNITY": "1", "EXPO_PUBLIC_APPLE_HEALTH": "1", "EXPO_PUBLIC_BARCODE_PROVIDER": "off" }
}
```

plus a submit profile `staging-testflight` (`"ios": {}`: it holds **no** Apple credential of any kind). Why each choice:

- `distribution: store`: App Store distribution signing, accepted by App Store Connect and TestFlight.
- `environment: staging`: URL and publishable key come from the EAS `staging` environment (the same one `staging-preview` already used), never from git.
- `autoIncrement: true` with `appVersionSource: remote`: EAS owns the build number so a re-upload never collides.
- `EXPO_PUBLIC_APP_ENV=preview`, never `production`: a TestFlight build of the staging backend must not be mistaken for a release build, and the production guards (which would refuse Community, Friends and Health) stay out of the way. Production remains untouched.
- Same flags as `staging-preview` (a test fails if they ever drift), plus `EXPO_PUBLIC_BARCODE_PROVIDER=off`: without it a preview build defaults to the **synthetic** barcode sample list, which testers would see as real products.
- Not set, on purpose: `EXPO_PUBLIC_CONTENT_FIXTURES` (existing policy and test: no EAS profile enables fixtures), `EXPO_PUBLIC_PRODUCTION_ACCOUNTS`, `EXPO_PUBLIC_AI_API_URL`.
  Tests added or updated (`buildConfig.test.ts`, `cloudBoundary.test.ts`): the profile list; store distribution and staging environment; never `production`; never mock; flags identical to `staging-preview` plus barcode off; no fixtures; no credential or URL in `eas.json` or the submit profile; the real profile environment resolves through the app's own config guard to staging, all features on, no mock, no samples, and refuses to start without the backend values or with a secret key. I could not validate the profile with `eas-cli` itself (it needs an Expo login even to print configuration); it uses only fields the existing profiles already use.

### 5a. Preparation (no build)

```bash
npm i -g eas-cli                 # version 16 or newer (help text checked with 27.10.0)
eas login && eas whoami          # the Expo account that will own the project
cd Dancehall-AI/apps/mobile
git checkout claude/ecstatic-meitner-8you9v && git pull --ff-only && git status -sb      # clean

eas init                         # [E1] link or create the EAS project; commit the app.json change it makes
eas env:set staging --name EXPO_PUBLIC_SUPABASE_URL --value https://bxhnrjulksganzydgrgm.supabase.co --visibility plaintext --non-interactive          # [E2]
eas env:set staging --name EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY --value 'sb_publishable_...' --visibility plaintext --non-interactive                     # [E2] publishable key only
eas env:list staging             # both variables must be listed
eas credentials -p ios           # [E3, E4] view the team, App ID, certificate and profile; change nothing you did not approve
eas build:version:set -p ios -e staging-testflight    # optional: choose the starting build number (EAS otherwise continues its own counter)
```

(`env:create` is deprecated in current `eas-cli`; `env:set` is its replacement. Whether a custom `staging` environment is available on your Expo plan is unverified: `eas env:list staging` will tell you. `EXPO_PUBLIC_` values are embedded in the app, so they are plain text by nature; the publishable key is designed to be public. A secret or service key is refused by the app and must never be used.)
